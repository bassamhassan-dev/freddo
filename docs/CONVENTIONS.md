# دستور فريدو (CONVENTIONS)

الملف ده هو **الدستور الثابت** للمشروع كله. أي كود جديد — مني أو من أي حد — لازم يمشي على القواعد دي. وكل قاعدة مكتوب جنبها **ليه** اتخذت، عشان تقدر تدافع عنها في أي إنترفيو، مش بس تحفظها.

آخر تحديث: Sprint 1.5 (الأساس).

**القاعدة الحاكمة فوق كل القواعد:** ممنوع الـ over-engineering. كل حاجة في المشروع بحجمها بالظبط — ستاندرد، مجرّبة، ومفيهاش سطر زيادة. لو شككت إن حاجة أكبر من اللازم، غالبًا كده فعلًا: امسحها. قسم 7 تحت مكتوب فيه بالاسم إيه اللي قررنا **مش** نعمله وليه.

---

## 1. شكل المشروع

```
server/src/
├── index.js                  ← التشغيل: يوصل بقاعدة البيانات ويفتح البورت
├── app.js                    ← تجميع الـ Express app (middlewares + routers)
├── config/
│   └── db.js                 ← الاتصال بمونجو (MONGO_URI من .env بس)
├── utils/                    ← أدوات عامة ملهاش علاقة بفيتشر معينة
│   ├── AppError.js
│   ├── catchAsync.js
│   └── apiResponse.js
├── middleware/               ← حاجات بتشتغل على كل الطلبات
│   ├── notFound.js
│   └── globalErrorHandler.js
├── features/                 ← كل فيتشر في فولدر واحد، كل طبقاتها جواه
│   ├── health/
│   │   └── health.routes.js
│   └── menu/
│       ├── menu.routes.js
│       ├── menu.controller.js
│       ├── menu.service.js
│       └── menuItem.model.js
└── seed/
    └── seed.js
```

**القاعدة:** مفيش فولدرات على مستوى المشروع اسمها `controllers/` أو `services/` أو `routes/` تلم كل حاجة. كل فيتشر عايشة في فولدر واحد (`features/menu/`).

**ليه؟** لما تيجي تعدّل في المنيو، كل اللي يخصه في مكان واحد مش موزع على 4 فولدرات. ولما المنيو يكبر ونحتاج نقسمه مايكروسيرفيس يومًا ما، الفولدر ده هو اللي يتنقل بحاله. التجميع بالطبقة (كل الكنترولرز مع بعض) بيخلي أي تعديل يلمس 4 أماكن، والتجميع بالفيتشر بيخلي التعديل في مكان واحد. ده اسمه *colocation* وده المعمول به في المشاريع الحديثة (2026).

## 2. الطبقات: routes → controllers → services → models

كل فيتشر متقسمة 4 طبقات، والاتجاه **اتجاه واحد بس** — كل طبقة بتكلم اللي تحتها ومحدش بيرجع لفوق:

| الطبقة | الملف | مسؤوليتها | ممنوع فيها |
|---|---|---|---|
| Routes | `menu.routes.js` | ربط الـ URLs بالكنترولرز. سطر واحد لكل endpoint | أي منطق. لو فيها `if` يبقى غلط |
| Controllers | `menu.controller.js` | حافة الـ HTTP: يقرأ الريكويست، ينضّف المدخلات، ينادي السيرفيس، يرد بـ `sendSuccess` | منطق بيزنس، كلام مباشر مع Mongoose |
| Services | `menu.service.js` | **كل منطق البيزنس هنا**: فلترة، قواعد، قرارات | أي حاجة ليها علاقة بـ HTTP (مفيش `req`/`res` أبدًا) |
| Models | `menuItem.model.js` | تعريف الداتا: schema، validation، indexes، serializers | أي معرفة بوجود API أصلًا |

**أمثلة على التقسيم:**

- "الأصناف المخفية متظهرش في المنيو" → قاعدة بيزنس → **service** (`isAvailable: true` جوه الكويري).
- "?category جاية string ولا لأ" → تنضيف مدخلات HTTP → **controller**.
- "السعر مينفعش يبقى سالب" → قاعدة على الداتا نفسها → **model** (`min: 0`).

**ليه service منفصلة أصلًا؟** 3 أسباب ملموسين:

1. **اختبار أسهل:** السيرفيس بتتست من غير HTTP ولا سيرفر شغال.
2. **إعادة استخدام:** نفس `listAvailableItems` هيستخدمها الأدمن بانل، والـ seed، وأي background job بعدين. لو المنطق في الكنترولر هيتكرر كوبي بيست.
3. **كنترولر رفيع:** الكنترولر اللي فيه منطق هو أكتر مكان بيتخن ويتبهدل في مشاريع إكسبريس. القاعدة دي بتمنع ده من الأول.

**ليه مفيش Repository layer فوق Mongoose؟** عن قصد. Mongoose نفسه هو الـ repository: بيديك `find`/`findOne` جاهزين. طبقة زيادة هتحط فانكشن بترمي على فانكشن من غير ما تضيف حاجة — ده over-engineering، وهنزوده **بس** لو حطينا ORM تاني أو احتجنا نبدل الداتابيز فعلًا.

## 3. شكل الرد الموحد (API response shape)

**أي نجاح** في الـ API كله:

```json
{ "success": true, "data": { "items": [ ... ] } }
```

**أي خطأ** في الـ API كله:

```json
{
  "success": false,
  "error": {
    "code": "ITEM_NOT_FOUND",
    "message": { "ar": "الصنف ده مش موجود في المنيو", "en": "This item is not on the menu" }
  }
}
```

**القواعد:**

- الفرونت إند بيبص على `success` الأول. بعدها ياخد `data` أو `error`. مش محتاج يخمن شكل الرد من endpoint للتاني.
- الـ HTTP status هو اللي بيحمل المعنى (200 نجاح، 400 مدخلات غلط، 404 مش موجود، 409 تكرار، 500 خطأ مننا). مش بنكتب status جوه الـ body.
- `error.code` نص ثابت UPPER_SNAKE. الفرونت إند بيتفرّع عليه (`if (code === 'ITEM_NOT_FOUND')`)، **مش** على نص الرسالة — الرسالة ممكن تتغير، الكود لأ.
- الرسالة دايمًا بلغتين `ar` + `en`. الفرونت إند بيعرض لغة الواجهة الحالية. السيرفر مش بيعرف الواجهة بأي لغة ولا محتاج يعرف.
- مفيش `meta` ولا `pagination` ولا أي مفاتيح زيادة. هتتضاف **لما** يبقى فيه endpoint محتاجها فعلًا، مش قبل كده (YAGNI).

**ليه الشكل ده بالذات؟** بدائل مشهورة: JSend (`status: success/fail/error` بـ 3 قيم) وJSON:API (ثقيل جدًا ومعمول للعلاقات المعقدة). اخترنا أبسط شكل بيحقق الهدف: مفتاح واحد للتمييز + data + error ثنائي اللغة. أي حد يقرأ الرد يفهمه من أول نظرة.

## 4. معالجة الأخطاء

### 4.1 `AppError` — الخطأ المقصود الوحيد

```js
throw new AppError(404, 'ITEM_NOT_FOUND', 'الصنف ده مش موجود في المنيو', 'This item is not on the menu');
```

أي خطأ **متوقع** في البيزنس (مش موجود، مدخلات غلط، مكرر) بيترمي كـ `AppError`. حقل `isOperational = true` بيفرّقه من bugs البرمجة (زي `TypeError`) اللي `isOperational` بتاعها false.

**ليه الفرق ده مهم؟** الخطأ المتوقع له رسالة آمنة تتعرض للعميل. الـ bug رسالته ممكن تسرب تفاصيل داخلية (مسارات، أسماء جداول، قيم)، فبيترد بـ 500 عامة والتفاصيل بتتسجل عندنا بس.

### 4.2 `catchAsync` — وداعًا try/catch

إكسبريس 4 مش بيمسك الأخطاء اللي جوه async handlers لوحدها. بدل ما كل راوت يكتب try/catch شغلانته الوحيدة `next(err)`، بنلف الهاندلر مرة واحدة:

```js
export const getMenu = catchAsync(async (req, res) => { ... });
```

أي rejection بتوصل `globalErrorHandler` لوحدها. **القاعدة:** ممنوع try/catch في الكنترولرز إلا لو بتعمل recovery حقيقي (مش مجرد تمرير).

### 4.3 `notFound` + `globalErrorHandler` — آخر محطتين

في `app.js`، بعد كل الراوترز:

```js
app.use(notFound);            // أي URL مطابقش حاجة → AppError 404
app.use(globalErrorHandler);  // أي خطأ في أي حتة → رد واحد موحد
```

`notFound` **بيبني** الخطأ بس؛ اللي **بيكتب** الرد دايمًا `globalErrorHandler`. كده الـ 404 بتاع URL غلط شكله بالظبط زي الـ 404 بتاع صنف مش موجود.

`globalErrorHandler` كمان بيترجم أخطاء مونجو لغتنا: `CastError` ← 400 `INVALID_ID`، `ValidationError` ← 400 `VALIDATION_ERROR`، duplicate key (11000) ← 409 `DUPLICATE`. السيرفيسز والكنترولرز مش محتاجة تعرف يعني إيه CastError أصلًا.

**ليه مكان واحد بيكتب أخطاء؟** لو كل راوت بيكتب الخطأ بتاعه، الشكل هيتلخبط مع أول مطور جديد أو أول يوم مستعجل. مكان واحد = شكل واحد مضمون.

## 5. التسمية

- **فولدر الفيتشر:** camelCase مفرد: `menu/`, `order/`, `auth/`.
- **الملفات جواها:** `<feature>.<role>.js`: `menu.routes.js`, `menu.controller.js`, `menu.service.js`, `menuItem.model.js`. اسم الملف بيقول هو أنهي طبقة.
- **الأدوات العامة:** camelCase واصف: `AppError.js` (class فـ PascalCase زي اسم الكلاس), `catchAsync.js`, `apiResponse.js`.
- **error codes:** UPPER_SNAKE_CASE، إنجليزي، ثابت: `ITEM_NOT_FOUND`, `VALIDATION_ERROR`.
- **الفانكشنز:** أفعال: `listAvailableItems` مش `getMenuItemsService`.

## 6. إزاي تضيف فيتشر جديدة (مثال: الطلبات `order`)

نفس الخطوات كل مرة، بالترتيب:

1. **الموديل** `features/order/order.model.js`: الـ schema + validation + `toPublicJSON` (لو هيتعرض بره).
2. **السيرفيس** `features/order/order.service.js`: فانكشنز المنطق كلها، بترمي `AppError` لما حاجة تبوظ.
3. **الكنترولر** `features/order/order.controller.js`: هاندلرز ملفوفة بـ `catchAsync`، بتنضف المدخلات وبترد بـ `sendSuccess`.
4. **الراوتس** `features/order/order.routes.js`: سطر لكل endpoint.
5. **التوصيل** في `app.js`: `app.use('/api/orders', orderRouter);` — الراوتر الجديد بيركب **فوق** سطر `notFound` دايمًا.
6. **الاختبارات** `server/test/order.test.js`: شغال على mongodb-memory-server (داتابيز حقيقية في الذاكرة، من غير أي connection string).

لو الفيتشر بتحتاج middleware خاص بيها (زي auth)، بيتحط في `middleware/` برضه بس باسم واصف (`auth.js`) ومبيتركبش على مستوى الـ app إلا لو لكل الطلبات.

## 7. قرارات متعمدة (إيه اللي عن قصد مش بنعمله)

دي حاجات هتتسأل عنها أو هتشوفها في مشاريع تانية. جاوبنا عليها من الأول:

- **مفيش interface لكل فانكشن / ملف لكل كلاس (ستايل جافا/C#).** جافاسكربت مش محتاج العقود دي عشان تشتغل. عقدنا هو **الاختبارات + الشكل الموحد للرد**. interfaces حقيقية (TypeScript) ممكن تيجي لو المشروع تحول TS، مش قبل كده.
- **مفيش Dependency Injection container.** السيرفيسز فانكشنز عادية بتتعملها import مباشرة. DI containers بتحل مشكلة "تبديل التنفيذ وقت التشغيل" وإحنا معندناش المشكلة دي — وثمنها تعقيد قراءة الكود كله.
- **مفيش Repository layer فوق Mongoose.** (شوف 2 فوق).
- **مفيش classes في السيرفيسز.** `menu.service.js` فيه فانكشنز مصدّرة، مش class. الكلاس بيدي state وinheritance وإحنا مش محتاجين لا ده ولا ده — فانكشن نقية أبسط وأسهل في الاختبار.
- **مفيش barrel files (index.js بتجمّع وبتصدّر كل حاجة).** بيخفوا الـ imports الحقيقية وبيعملوا circular dependencies بسهولة. كل ملف بيعمل import للي محتاجه بالظبط.
- **المنيو بيفلتر المخفي في الداتابيز مش في الفرونت.** `isAvailable: true` جوه الكويري. الفلترة على العميل معناها إن الصنف المخفي بيتبعت للمتصفح أصلًا — وده تسريب.
- **الرسائل ثنائية اللغة من أول يوم.** الترجمة "بعدين" معناها تعديل كل مكان كتب رسالة. `ar`/`en` من الأول كلفتها صفر دلوقتي وكبيرة لو اتأخرت.
- **التفاصيل الداخلية مبتعدتش للعميل أبدًا.** الـ 500 دايمًا رسالة عامة، والحقيقية في اللوجز. الـ stack trace مبيتبعتش بره ولا حتى في development — العادة الصح من الأول.

## 8. الاختبارات

- **السيرفر:** `node --test` الأصلي بتاع Node + `mongodb-memory-server`. مفيش connection string حقيقي في أي اختبار، ومفيش mocking لمونجو — الاختبارات بتجري على مونجو حقيقي في الذاكرة فبتصيد أخطاء حقيقية (validation, indexes, queries).
- **العميل:** Vitest + Testing Library، والـ fetch بيتعمله mock.
- **لازم يفضلوا خضر:** `npm test` في الـ server وفي الـ client قبل أي push.
- **أي قاعدة بيزنس جديدة = اختبار جديد.** القاعدة من غير اختبار مالهاش وجود.
