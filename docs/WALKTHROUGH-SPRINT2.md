# Freddo - Sprint 2: الحسابات والدخول (Auth)

الملف ده شرح بالمصري لكل قرار اتاخد في Sprint 2. القواعد العامة في
`docs/CONVENTIONS.md` — هنا بنشرح الـ auth بالتحديد، عشان ده أكتر مكان
بتتسأل عنه في الإنترفيوهات.

## إيه اللي اتعمل؟

1. **تسجيل عميل جديد** (`POST /api/auth/register`) — اسم + إيميل + باسورد.
2. **دخول موحد لكل الأدوار** (`POST /api/auth/login`) — صفحة واحدة،
   والباك إند هو اللي بيقول انت مين، والفرونت بيوديك على حسب دورك.
3. **خروج** (`POST /api/auth/logout`) — بيلغي الجلسة من السيرفر مش بس من
   المتصفح.
4. **تجديد صامت للجلسة** (`POST /api/auth/refresh`) — المستخدم ميسجلش
   دخول كل 15 دقيقة.
5. **مين أنا** (`GET /api/auth/me`) — بيانات الحساب الحالي.
6. **صفحات الفرونت:** دخول، تسجيل، حسابي، وصفحات مؤقتة لمناطق الأدمن
   والباريستا + حماية للصفحات المحتاجة دخول.
7. **أول حساب أدمن** بيتعمل من الـ seed (من `.env` بس، مش من الكود).

## الـ tokens: إزاي الجلسة شغالة؟

عندنا **توكينز من نوعين**، وده النمط الستاندرد في 2026:

| | Access token | Refresh token |
|---|---|---|
| عمره | 15 دقيقة | 7 أيام |
| بيتخزن فين | ذاكرة المتصفح بس (JavaScript variable) | كوكي `HttpOnly` |
| بيتبعت إزاي | هيدر `Authorization: Bearer` | الكوكي بتروح لوحدها على `/api/auth/*` بس |
| لو اتسرق | يعيش 15 دقيقة بس | مبيقدرش يتقري من JavaScript أصلًا |

**ليه الـ access token في الذاكرة مش في localStorage؟** أي كود خبيث بيشتغل
في الصفحة (XSS) يقدر يقرأ localStorage. الذاكرة العادية أصعب بكتير،
والأسوأ اللي يحصل إن الصفحة لما تتقفل التوكين يضيع — وده بيتعوّض فورًا
بالـ refresh cookie.

**ليه الـ refresh في كوكي HttpOnly؟** عشان JavaScript **مش بيشوفه خالص**،
فمستحيل يتسرق بـ XSS. ومتقيد بـ `Path=/api/auth` فمبيروحش لأي endpoint
تاني، و`SameSite=Lax` بيمنع المتصفح من إنه يبعته من موقع تاني — ودي
إجابتنا لسؤال CSRF. باقي الـ endpoints أصلًا بتشتغل بهيدر Authorization،
والمتصفح مبيضيفش الهيدر ده من نفسه، فمفيش CSRF عليها.

## الـ rotation والحماية من السرقة

كل مرة الـ refresh token بيتستخدم، **بيتمسح ويتبدل بجديد**. يعني كل توكين
بيشتغل **مرة واحدة بس**. لو حد سرق توكين قديم وحاول يستخدمه، السيرفر
يلاقيه مش موجود في قاعدة البيانات رغم إن التوقيع صح — ده معناه إن التوكين
ده اتبدل قبل كده (أو اتسرق واتعاد استخدامه)، فبنلغي **كل جلسات المستخدم**
فورًا ونطلب دخول جديد. ده اسمه reuse detection.

**التوكينز متخزّنة hashed (SHA-256) في قاعدة البيانات.** لو الداتابيز
اتسربت، اللي يطلع منها هاشات مش توكينز شغالة. استخدمنا SHA-256 مش bcrypt
هنا عن قصد: التوكين نص عشوائي طويل أصلًا (مش باسورد بشري سهل التخمين)،
فالتهديد هو التسريب مش التخمين.

## ليه MongoDB للجلسات مش Redis؟

الدوكيومنت الأصلي كان ماشي في اتجاه Redis. اخترنا MongoDB عن قصد
(موثق في CONVENTIONS قسم 7):

- بنية أقل بقطعة كاملة — مفيش Redis تاني يتنصب ويتدار.
- TTL index بيمسح الجلسات المنتهية لوحده.
- المنطق (rotation + revocation + reuse detection) **نفسه بالظبط** —
  المخزن مجرد تفصيلة تنفيذ.
- لو الأداء احتاج Redis يومًا، ملف واحد هو نقطة التبديل
  (`refreshToken.model.js`).

## القواعد الأمنية اللي اتطبقت (doc 22)

- الباسورد بيتخزن **bcrypt** (cost 12) ولا مرة plain. الحقل نفسه
  `select: false` في Mongoose فمبيطلعش في أي query إلا لو طلبناه بالاسم
  (وفي مكان واحد بس: الـ login).
- الإيميل بيتوحّد (lowercase + trim) قبل التخزين، فـ `Bassam@X.com` و
  `bassam@x.com` نفس الحساب — والـ unique index بيضمن مفيش تكرار.
- رسالة خطأ **واحدة** لـ "إيميل مش موجود" و"باسورد غلط": الـ API مبيقولش
  أنهي إيميلات متسجلة.
- التسجيل العام بيعمل **عميل بس**. لو حد بعت `role: "admin"` في الريكويست،
  بنتجاهله — بناخد الحقول واحدة واحدة بالاسم (مفيش spread للـ body)، فمفيش
  mass assignment.
- الحسابات الموقوفة (`isActive: false`) مبتدخلش، والجلسات القديمة بتاعته
  بتترفض أول ما يحاول يعمل refresh.
- **rate limit** على register/login: 30 محاولة كل 15 دقيقة لكل IP
  (بتتقفل في التستات).
- **Helmet** بيضيف هيدرز الأمان الستاندرد على كل الردود.
- أي رد عن مستخدم بيعدي على `toPublicJSON` — مفيش `passwordHash` ولا
  أي حقل داخلي بيعدي للفرونت.

## الفرونت إند

- **Zustand** store للجلسة (user + status). خفيف (1KB) ومش محتاج boilerplate
  بتاع Redux — ده اختيار الدوكيومنت أصلًا (19.2).
- **React Router** دخل المشروع: `/` المنيو، `/login`، `/register`،
  `/account` (محمي)، `/admin` و`/barista` (صفحات مؤقتة)، و404.
- أول ما الأب يفتح، `bootstrap()` بيجرب refresh صامت — لو فيه جلسة،
  المستخدم يلاقي نفسه داخل من غير ما يحس.
- الـ API client فيه **إعادة محاولة واحدة**: لو رد 401 جاب من endpoint
  عادي، بيجرب يعمل refresh مرة واحدة ويكرر الطلب. وطبعًا endpoints الـ auth
  نفسها مستثناة من ده (401 من login/refresh إجابة نهائية — ودي غلطة اتصلحت
  ومعمولها regression test: `client.test.js`).
- خريطة التوجيه حسب الدور في ملف واحد (`auth/roleRedirect.js`): أدمن ←
  `/admin`، باريستا ← `/barista`، عميل ← `/`.

## إزاي تجرب على جهازك

```bash
# في server/.env ضيف:
JWT_ACCESS_SECRET=<نص عشوائي طويل>
JWT_REFRESH_SECRET=<نص عشوائي طويل تاني>
ADMIN_EMAIL=admin@freddo.com
ADMIN_PASSWORD=<باسورد الأدمن بتاعك>

npm run seed    # هيحمل المنيو + يعمل حساب الأدمن
npm run dev     # وافتح http://localhost:5173/register
```

توليد نص عشوائي للأسرار:
`node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`
